# 研修と教材に使う

[README](../README.md) — 社内 Web サービスの研修、スクールの教材に回すときの話。

**新規実装は要らない。** Web の自動収録は元々の本命で、
[GlossPop の 1 本](https://lancard-aikawa.github.io/GhostMoviePlayGallery/v/glosspop.html)が
実在のプロジェクトを撮った例。ここに書くのは**対象の選び方と、SaaS を相手にしたときの壁**。

## なぜ相性が良いか

| | |
| --- | --- |
| **撮り直しが無料** | 教材は毎期作り直す。口調の差し替えも多言語も `say` を書き換えて `render` し直すだけで、**絵は 1 回撮ったきり** |
| **狙って失敗できる** | 研修で効くのは操作の羅列ではなく、**受講者が実際に踏む失敗**。ソースを読んだ AI が設計する（[統治と習慣](governance.md)と同じ考え方） |
| **手を動かさせるところまで届く** | 設定一式を配れば、観るだけで終わらせない（[README_BUNDLE.md](../README_BUNDLE.md)） |

## いちばん大事なこと —— 撮る対象を分ける

| 撮る相手 | 自動収録 | [`gmp check`](check.md) | 実データ |
| --- | --- | --- | --- |
| **自社の社内 Web サービス** | **通る** | **効く**（撮り直して赤を数える） | 研修用のデータを `app.setup` で仕込める |
| **SaaS の画面**（Microsoft 365 / Google Workspace） | **サインインで止まる** | **効かない** | 本番テナントを撮ると氏名・メール・顧客名が載る |

**1 本の中で混ぜない。** 自社アプリと SaaS を跨ぐ 1 本にすると、**いちばん弱いところに
全体が引きずられる** —— 自動収録できず、検査もできず、撮り直しが手作業の 1 本になる。
分けておけば、自社側だけは決定論のまま回り続ける。

## SSO の壁（Microsoft / Google）

**自動化ブラウザからのサインインは弾かれる。** 2 段階認証や端末確認も挟まる
（[plan.md のログインの節](plan.md#ログインが要るアプリを撮る)）。逃げ道は 3 つ。

1. **そこだけ人が撮る。** [支援収録](../README_WINAPP.md)は Windows アプリ専用ではない ——
   `app.window` にブラウザのウィンドウを書けば、**Web でも同じ道が使える**
2. **サインインを画に入れない。** 「ログイン済みの状態から」始める台本にして、
   入口は静止画 1 枚か文章で済ませる。**研修で見せたいのはログインの先**
3. **自社側でセッションを埋める。** 自分で立てられるアプリだけ。収録用サーバの中で
   認証チェックより先にセッションを作る（[plan.md](plan.md#ログインが要るアプリを撮る)）

**資格情報を `plan.json` に書くのは撮影用アカウントだけ。** 素の form ログインなら
台本に書くのがいちばん壊れにくいが、書いた瞬間そのファイルは配れなくなる。

**壁そのものを道具の側で外す案**は[実ブラウザで撮る](ideas/browser.md)に置いてある
（人がサインイン済みのプロファイルで撮る）。**引き換えに「誰が撮っても同じ」が消える**
ので、まだ入れていない。

## 実データを映さない

**本番テナントで撮らない。** 研修用テナントかサンドボックスを用意して、
中身は `app.setup` で仕込む。SaaS は**画面のあちこちに人の名前が出る** ——
ヘッダのアカウント名、共有相手、通知、最近使ったファイル、履歴。

**これは「気をつける」で防げない。** このリポジトリだけでも、動画・サムネ・
ドキュメントの画像で**ユーザー名を 3 回載せた**（どれも出す直前まで気づいていない）。
**人の目ではなく道具で止めること** —— Gallery の `build.py` が、束の中に
ユーザー名を含むパスがあれば配布物を吐かずに落ちる、という形にしてある。

## 腐り方が違う

自社アプリは**こちらの都合で止められる**が、SaaS は**勝手に変わる**。
UI が変わった瞬間に、教材は黙って嘘になる。

- `gmp check` が撮り直して赤を数えられるのは、**ログインの壁が無い相手だけ**。
  支援収録に落とした 1 本は検査できない（`--` になる。それが正しい）
- だから **SaaS の画面は「腐る前提」で短く作る。** 長い 1 本より、
  差し替えやすい短い複数本にしておくと、変わったところだけ撮り直せる
- 自社アプリ側は逆に、**台本と対象が同じリポジトリにあるなら CI で回る**（[check.md](check.md#ci-で回す候補このリポジトリでは回していない)）

## スクール（教育事業）で効くところ

- **同じ題材を毎期作り直す**ので、撮り直しが無料なのがそのまま効く
- **受講者に配って手を動かさせる**（[README_BUNDLE.md](../README_BUNDLE.md)）。
  観るだけの教材と、同じ環境を手元に作れる教材は別物
- **多言語は `say` の差し替えだけ。** 1 収録から複数言語が設計上すでに出せる
  （束ねる口が無いだけ —— [アイデア A](ideas/README.md#a-媒体を差し替える)）
- **題材選びが質を決める。** Pass1 に「操作を並べて」と頼むと紙芝居になる。
  「受講者が実際に踏む失敗」を頼むこと

## 始め方

1. **自社の 1 画面で 1 本撮る**（自動収録・研修用データ・3 幕構成）
2. `gmp check` を CI に置く（[check.md](check.md)）—— 対象と台本が同じリポジトリなら効く
3. **束を配る**（[README_BUNDLE.md](../README_BUNDLE.md)）
4. **SaaS の画面が要るところだけ**支援収録に落とす（[README_WINAPP.md](../README_WINAPP.md)）

**1 と 2 を先にやること。** 4 から始めると、いちばん腐りやすく検査もできない側から
教材が増えていく。
