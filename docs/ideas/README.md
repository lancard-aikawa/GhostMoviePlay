# アイデア

[README](../../README.md) — **まだ作っていないもの**の置き場。決まったことは書かない。
実装したら、ここから消して `docs/` の本編か [CLAUDE.md](../../CLAUDE.md) に移す。

README の[未実装](../../README.md#未実装)が「この延長線上にある穴埋め」なのに対し、
ここは **道具の形そのものを変える案**を置く。

## 芯にあるもの

発展形を考えるときの起点。このツールの価値は mp4 ではなく、次の 3 つにある。

1. **AI の仕事は「操作」ではなく「演目の設計」。** ソースを読んで
   *人が分からなくて離れてしまうところを狙って作れる* ことが価値であって、
   UI を自動操作すること自体には価値がない。**軸は離脱**で、**失敗はその一種**。
   目的との食い違い・選べなさ・順序の縛り・引き返せなさも、同じだけ人を離れさせる
2. **`plan.json` という人が直せる中間表現**で AI と収録を切り離した
3. **リプレイが決定論的**なので撮り直しが無料

**3 つとも動画に固有ではない。** 発展の余地は全部そこにある。

## A. 媒体を差し替える

`plan.json` は動画専用フォーマットではない。`render` の隣にもう一つレンダラを置く話。

| 出力 | 中身 |
| --- | --- |
| 手順書 (md) | 各ビート = スクショ + 原稿。**動画と手順書が食い違いようがない**（下を見よ） |
| README 用 GIF / APNG | 音声なし・字幕だけの短縮版 |
| スライド | シーン = 章、ビート = ページ |
| アプリ内ツアー | coach mark 形式。`actions` の selector をそのまま使える |
| 多言語同時出し | `say` だけ差し替えて 1 収録から複数言語。設計上すでに可能で、束ねる口が無いだけ |

**対話型**が一番面白い。決定論なので「ビート k の直前状態」を再現できるから、
動画の途中で「ここから自分でやってみる」と実アプリに受け渡せる。
引っかかるところを見せた直後に操作を渡す、という教材になる。

**[教える側へ回す案](coach.md)は、その支援収録版。** あちらは決定論が要らない
—— 操作するのが最初から人なので、**`gmp shoot` の画面がほぼそのまま教材の器になる**。
新しく書くのは「相手を見つける・入れさせる」「1 ビートを全文で読ませる」
「出来たら次へ」だけで、撮る部分は 1 行も要らない。

**手順書 (md) はいつでも作れる状態にある。** 静止画を抜く仕組みは台本エディタの
サムネイルで出来ている (`ffmpeg.frame_at`) ので、`timing.json` + `raw.webm` から
`guide.py` が 80 行ほどで届く（`gmp render` の隣にもう 1 つ出口を置くだけ。AI も
撮り直しも要らない）。**作っていないのは宛先が無いから。** 出来るのは*出力物*で
あって道具の形は変わらないので、配る先（README・社内 wiki・顧客向けの手順書）が
決まるまでは、腐る素材が 1 種類増えるだけになる。「媒体中立の実証になる」は
主張であって用途ではない。

## B. 目的を差し替える —— 撮る道具から、検査する道具へ

`gmp record` は要するに**ナレーション付きの Playwright スクリプト**なので、
落ちたということは UI が変わったということ。

**ドキュメント腐敗検知は入った** —— `gmp check` が全部の `plan.json` を撮り直して
赤を数える（[docs/check.md](../check.md)）。残りはこの 2 つ。

- **ビート単位のビジュアル回帰。** ビートに id があるので、差分の指し先を
  「どの説明が壊れたか」で出せる
- **リリース差分動画。** 2 つの tag で同じ plan を撮って並べる、または変わった
  ビートだけ撮り直す

## C. 対象を差し替える

`record` を挿げ替えれば `plan` / `voice` / `render` はそのまま使える。

- **[Android アプリ](android.md)** —— 見積り済み。Pass2 だけの差し替えで届く
- **[Windows デスクトップアプリ](desktop.md)** —— 見積り済み。UI Automation に
  selector があるので決定論を保てる。**届かない相手を人が撮る道 (支援収録) は入った**
  ので、残りは「人の代わりに操作する部分」だけ
- **[実ブラウザで撮る](browser.md)** —— 対象は Web のままで、**駆動を差し替える**。
  人がサインイン済みのプロファイルで撮れば、SaaS（Microsoft 365 / Google
  Workspace）の壁が外れる。**Playwright は捨てなくてよい**（`launch_persistent_context`）。
  引き換えに「誰が撮っても同じ」が消えるので、束としては配れなくなる
- CLI / TUI（pty リプレイ）
- API シーケンス（リクエストとレスポンスを画面に見立てる）
- canvas / WebGL、Jupyter、複数アプリを跨ぐ業務フロー

## D. 「問題を狙って作る」だけを取り出す

動画を作らなくても単体で価値がある部分。Pass1 の出力先を変えるだけ。

- **落とし穴監査。** ソースを読んで「ユーザーが踏む典型的な悪手」を列挙・ランク付け
  するレポート。GlossPop の「短い語を登録すると本文がリンクだらけになる」がまさにこれで、
  *動画にする前の段階に既に価値がある*。悪習カタログを題材にする撮り方は
  [統治と習慣を撮る](../governance.md)（**こちらは既存機能だけで回るので ideas ではない**）
- **演習問題ジェネレータ。** 悪手を仕込んだ状態を配って直させる
- **QA のテストケース生成。** 正常系ではなく誤操作パスを吐かせる
- **逆変換。** 人の実操作を録って `plan.json` に起こし、AI に「何が悪かったか」を
  後付けさせる。サポート issue → 再現＋解説動画。AI が UI を読み切れないとき
  （canvas、ログイン必須、業務アプリ）の入口としても効く。

  **Web なら入口が既にある** —— Chrome の DevTools Recorder が人の操作を JSON で
  書き出すので、`ACTION_SPECS` への対応表 1 枚で届く。しかも**記録するのは本人が
  サインイン済みの実ブラウザ**なので、SaaS の壁をそもそも通らない
  （[browser.md](browser.md#起こす--変換器を作るのがいちばん現実的)）。

  **操作するのは人でなくてよい** —— AI に `do` を読ませて 1 回だけ操作させ、
  それを `actions` に起こせば、そこから先は決定論に戻る
  （[desktop.md の「人の代わりを AI にやらせる」](desktop.md#人の代わりを-ai-にやらせる駆動の当て)）。
  **出てくるのは同じ「操作の列」なので、変換器の入口が 1 つ増えるだけ**

## 見立て

**出力物が増えるだけの案は上に置かない。** 配る先が決まっていないものを先に
作ると、腐る素材が増えて、道具の形は変わらないまま手間だけ残る
（手順書レンダラはそれで下げた）。

1. **D の逆変換。** 「AI に撮らせる」の反対側が埋まる。**制約の迂回そのものは
   [支援収録](../plan.md#自動操作が届かない相手を撮る支援収録)で入った**（canvas・
   ログイン必須・業務アプリを人が撮れる）ので、残っているのは**操作を録って
   `plan.json` に起こす**ところ —— 人の操作が台本になれば、そこから先はまた決定論に戻る
2. **B の残り（ビート単位のビジュアル回帰）。** `gmp check` は selector が在るかまでしか
   言えない。「説明と画面が食い違っていない」を言うにはここが要る
3. **[教える側へ回す](coach.md)の第一歩。** 台本を読んで 1 ビートを全文で出すだけの
   窓を作り、**Krita の 1 本を人に通してもらう**。分かるのは「`do` が撮る人ではなく
   教わる人に通じるか」の 1 点だけだが、**通じないなら直すのは Pass1 の書かせ方**で、
   それは動画の側にも効く。**いちばん安く試せて、外れても無駄にならない**

[Android](android.md) と [Windows デスクトップ](desktop.md) は単体では 1〜2 より
重いが、**オーバーレイを render 時に移す**という副産物が Web 側にも効く。
**2 つが別々の道から同じ部品を要求している**ので、そこだけ先に切り出す価値がある。

**同じことが「配る」にも言える。** [教える側へ回す](coach.md)も
[AI に操作させる](desktop.md#人の代わりを-ai-にやらせる駆動の当て)も、
**手順の一式が相手の機械に届くこと**を前提にしている
（[手順を束ねて配る](bundle.md)）。**束の形は既にある**（1 本 = 1 フォルダ）ので、
要るのは運び方 —— ただし **`plan.json` は相手の機械で走るコマンドを持っている**
ので、順番を間違えると「落として走る」危ない道具が先に出来る。
先に作るのは**走らせる前に見せる**ほうと、**上げる前に止める**ほう。

**逸らす手を試す相手も決まっている** —— `%APPDATA%` に置くアプリ（Krita /
Notepad++）と、**レジストリに置く 7-Zip**。後者は「効かない側」の確認で、
既に入っているので即試せる。梯子（環境変数 → ポータブル → レジストリ退避 → VM）の
どこに落ちるかが実データで決まる。

**デスクトップの次の一手は決まっている** —— 入力も窓の取り方も実測で通り、
人が撮る道 ([支援収録](../../README_WINAPP.md)) も入った。残っているのは
**「環境変数で書き込み先を逸らす手が実アプリで効くか」**だけで、効けば Web と
同じ強さの決定論が立つ。**対象を 1 つ選んで試すまで机上では詰められない。**
