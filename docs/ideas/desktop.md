# Windows デスクトップアプリを撮る

[アイデア](README.md) — 収録対象を Web から Windows のデスクトップアプリへ広げる案の
うち、**まだ作っていないほう** —— **自動で操作する (UIA ドライバ)**。
下の数字は 2026-08-25 に Windows 11 で実際に叩いて取ったもので、書いたら測り直すこと。

**UI Automation (UIA) が selector を持っている**ので、[Android](android.md) と同じ形
—— 差し替えが要るのは実質 **Pass2 だけ**で、`plan.json` / `timing.json` の境界の
おかげで Pass1 と Pass3 はほぼそのまま使える。

**ウィンドウを撮るところは既にある。** 人が操作して撮る道
（[支援収録](../plan.md#自動操作が届かない相手を撮る支援収録)）を入れたときに
`capture.py` を書いたので、`PrintWindow` も `gdigrab` もそのまま使える。
足りないのは**人の代わりに操作する部分**だけ。

## 段ごとの影響

| 段 | デスクトップで | 手間 |
| --- | --- | --- |
| `plan` (Pass1) | ソースが読めるとは限らない。selector が CSS → `AutomationId` / `Name` / `ControlType` | 中（`detect.py` 相当が効かない） |
| `voice` | **そのまま** | なし |
| `record` (Pass2) | Playwright → UIA、`record_video` → `PrintWindow` 連写か `gdigrab` | **中〜大** |
| `render` (Pass3) | ほぼそのまま。**カーソルが写らない**問題だけ（下記） | 小 |

`Recorder.play_beat` の「音声の尺がビートの尺を決める」「実測時刻を timing.json に
書く」は丸ごと生き残る。`Recorder.do()` の分岐も `click` / `type` / `press` /
`wait_for` が UIA と素直に対応する。**`select_text` は落ちる**（Android と同じ）。

## 実測できたこと

電卓を起こして **7 → `+` → 3 → Enter = 10** を自動操作し、その 7 秒を録画するところ
まで通した。

| やったこと | 手段 | 結果 |
| --- | --- | --- |
| 要素の列挙 | `AutomationElement.FindAll` | 53 要素。`AutomationId` と矩形とパターンが揃う |
| ポイント指定クリック | `SetCursorPos` + `mouse_event` | 通る。実カーソルが動く |
| セレクタ指定クリック | `InvokePattern.Invoke()` | 通る。カーソルを動かさない |
| キーボード | `keybd_event`（仮想キーコード） | 通る |
| 結果の読み返し | `Text` / `Value` パターン | `表示は 0 です` → `表示は 10 です` を逐一確認できた |
| ウィンドウ単独の静止画 | `PrintWindow(hwnd, hdc, 2)` | 通る。重なっていても画面外でも綺麗 |
| 動画 | `ffmpeg -f gdigrab` | 7.0 秒 / 105 フレーム / h264。取りこぼし無し |
| 日本語の入力 | `SendInput` の `KEYEVENTF_UNICODE` | **IME の状態に関わらず素通し**（下記） |
| 打鍵なしの入力 | `WM_SETTEXT` / `ValuePattern.SetValue` | 通る。ただし入力イベントが出ない |

## `type` は IME を経由してはいけない

`type` の実装候補を、使い捨ての入力欄（WinForms の TextBox）に対して 4 通り試した。
値はアプリ自身に書き出させて読んでいる。

| | 送ったもの | アプリが持った値 |
| --- | --- | --- |
| A. IME OFF + Unicode 注入 | `abc決定論🎬` | `abc決定論🎬` |
| B. **IME ON** + Unicode 注入 | `決定論` | `決定論` |
| C. IME ON + 普通の打鍵 | `k e t t e i` | **`''`（未確定）** → Enter 後に `けってい` |
| D. `WM_SETTEXT` | `直接設定 abc 🎬` | `直接設定 abc 🎬` |

**B が本命。** `KEYEVENTF_UNICODE` は IME を通らないので、**IME が日本語入力の状態でも
そのまま入る**。サロゲートペア（`🎬` = U+D83C U+DFAC）も 1 文字ずつ送るだけで復元される。
収録前に IME の状態を揃える必要すらない。

**C は使えない。** 打鍵は IME の未確定文字列に吸われるので、**アプリの値としては空**の
まま。しかも未確定は消えずに残り、検証中に**別の操作をした後で勝手に確定して混入した**
（`けってい直接設定 abc 🎬` になった）。「撮り直すたびに同じ絵になる」が根本から崩れる。

**D は逃げ道。** 入力イベントが出ないので、キー入力を見て動くアプリでは反応しない。
Playwright の `fill()` と `type()` の関係と同じで、既定は B、必要なら D。

## selector があることが全部の前提

```
Button  name='7'          id='num7Button'        rect=(52,351,77x51)   pat=[Invoke]
Button  name='プラス'      id='plusButton'        rect=(288,457,76x51)  pat=[Invoke]
Text    name='表示は 0 です' id='CalculatorResults'                      pat=[Text,Invoke]
```

座標クリックは解像度・ウィンドウ位置・DPI スケーリングのどれが変わっても壊れるので、
**リプレイに使えるのは `AutomationId` のほうだけ**。読み返せるパターン（`Text` /
`Value`）があるので、`wait_for` も「要素が在る」より強く書ける。

**`Name` で当ててはいけない。** 上のとおり `プラス` が返る —— **ロケール依存**なので、
英語環境のマシンで撮った瞬間に落ちる。「git に入る plan.json に機械依存の値を焼かない」
の一種で、`file:///C:/...` と同じ性質の事故になる。`AutomationId` は非依存。

### ただし selector の質はフレームワーク依存

同じ UIA でも、相手によって見え方がまるで違う。検証で使った WinForms のウィンドウはこうだった。

```
window: 'GMPTEST' class=WindowsForms10.Window.8.app...
descendants: 1
Pane  name='' id='32246994' rect=(688,427,544x201) pat=[]
```

**TextBox が `Pane` 1 個・パターン無し・数字の id で出てくる。** 電卓（WinUI）が
`num7Button` を出したのと同じ API でこれなので、**アプリ側が UIA プロバイダを
出していなければ何も掴めない**。id も実行のたびに変わる数字で、plan.json に焼けない。

これは [Android](android.md) の「Compose は既定で resource-id を持たない」と同じ問題
—— **対象アプリの協力が要る**のが Web との一番大きな違いで、`detect.py` 相当の推測が
やりにくくなる。**対象を選ぶ段階で UIA ツリーを見る**手順（`gmp doctor` の一部か、
Pass1 に渡すヒント）が要る。

## 本当に作り直しが要るのは 2 箇所

**1. `overlay.py`。** 疑似カーソル・波紋・ハイライト枠・黒みが全部「DOM に
`add_init_script` で注入した JS」なので、他人のアプリに潜り込めないここでは成立しない。
解は **収録時に描くのをやめて render 時に合成する**こと。

**これは [Android](android.md) がすでに出している結論と同じで、別の道から同じ部品に
着いた。** 2 つの案が同じものを要求しているので、**先に切り出す根拠が 1 つ増えた**。

**2. カーソル。** 実測で分かれた。

| | カーソル | 縁 |
| --- | --- | --- |
| `PrintWindow` | **写らない** | 綺麗。重なっても画面外でもウィンドウだけ |
| `gdigrab` | 写る | **漏れる**。不可視のリサイズ枠と角丸のぶん外が入り、手前のウィンドウも写る |

操作を見せる動画でカーソルが無いのは論外なので、**収録は `PrintWindow`（ウィンドウ単位）+
カーソル位置をイベントログに吐き、描くのは render** という形になる。つまり 1 と
同じ部品に帰着する。`gdigrab` をそのまま使う道は、縁の漏れがあるので採らない。

## 決定論は Web より難しい —— ここが本丸

Android がスナップショットで**むしろ楽**になったのと逆で、こちらは Web より弱い。

**口はすでにある。** 初期状態に戻す前処理は `plan.App` の `setup` が担当していて、
`server.prepared()` が `app.start` より前に走らせ、**落ちたら収録を止める**
（仕込めていない画面を撮っても意味が無いため）。デスクトップ版で新しい概念は要らない。

### 問題は「消す」か「逸らす」か

Web の仕込みは**使い捨てのデータルートを作る**（GlossPop の `serve.py`）ので非破壊
だが、デスクトップで素直に書くと**本物の `%APPDATA%` やレジストリを消す**ことになる。
撮る面のボタン 1 つでそれが走るのは危ない。**逸らすほうを既定にする。**

1. **環境変数で書き込み先を逸らす。** `app.start` は `shell=True` で走るので、
   `set APPDATA=<temp> && app.exe` の形で**今日書ける**。非破壊で、Web の使い捨て
   データルートと同じ性質になる
2. **ポータブル版 / プロファイル指定オプション**があるアプリならそれを使う
3. **`HKCU` のサブツリーを保存 → 復元**（`reg export` / `reg delete` / `reg import`）。
   破壊的だが可逆。1・2 が効かないアプリ向け
4. **VM / スナップショット。** Android のエミュレータ相当。いちばん強いが重く、
   `server.HOOK_TIMEOUT`（300 秒）に収まらない可能性がある

**後片付けの順序は既存の規則がそのまま効く** —— `prepared` が `serve` を包んでいるので
`teardown` はアプリを畳んだ後に走る。掴まれたままの一時ディレクトリを消しに行かない。

### 仕込みでは戻せないもの

- **時計。** `page.clock` に相当するものが無い。OS の時計を触るのは論外なので、
  アプリが表示する日時は固定できない
- **テーマ・DPI・言語。** ライト/ダーク、アクセントカラー、解像度、表示言語。
  [ビジュアル回帰](README.md#b-目的を差し替える--撮る道具から検査する道具へ)に
  使うなら、Android の SystemUI demo mode に相当する固定手段が要るが **無い**

**画面の他の状態は心配しなくていい。** `PrintWindow` はウィンドウ自身に描かせるので、
手前に別のウィンドウがあっても壁紙が違っても絵に入らない（実測）。デスクトップ全体を撮る
方式を採らない理由がここにもある。

**それでも「撮り直しが無料」は Web ほど強く成り立たない** —— 1 が効くアプリなら
ほぼ同じ強さになるが、3・4 に落ちるほど遅く、また重くなる。対象を選んで適用する話になる。

## 詰まるとしたら

- **UIA が届かない相手がある。** canvas・独自描画・ゲーム・リモートデスクトップ越し。
  Chromium / Electron は UIA クライアントが繋いだときに accessibility を有効化する
  はずだが **未検証**
- **Python から UIA を叩く手段が要る。** `uiautomation` / `pywinauto` / `comtypes` の
  どれかで依存が増える。**Windows PowerShell 5.1 を挟む道は採らない** ——
  UIA のアセンブリが WPF なので PowerShell 7 からは読めず、5.1 は
  **BOM の無い UTF-8 を cp932 と誤読して構文エラーになる**（実際に踏んだ。
  `clip` が UTF-16LE でないと読めないのと同じ家系）
- **`SetProcessDPIAware()` を先に呼ばないと座標がずれる。** 呼ばないプロセスから見た
  座標は OS に仮想化されるので、UIA が返す物理座標とかみ合わない
- **`SendInput` の `INPUT` は x64 で 40 バイト。** union の最大メンバが `MOUSEINPUT`
  なので、`KEYBDINPUT` だけで組むと 32 バイトになり `cbSize` 不一致で
  **`ERROR_INVALID_PARAMETER` (87) を返して 1 文字も入らない**（実際に踏んだ）。
  権限の問題に見えるが違う。ライブラリを使わず自前で叩くなら最初に確かめる
- **ストア配信アプリは launcher が別 PID に受け渡して終了する。** `Start-Process
  -PassThru` が返した PID の `MainWindowHandle` は永遠に 0 のまま（実際に踏んだ）。
  `app.start` から起こしたプロセスをそのまま掴む前提が崩れるので、**ウィンドウの側から
  掴み直す**必要がある
- **画面に意図しないものが載る。** 検証中、メモ帳が前のセッションのタブを復元して
  機密ファイル名を表示した。撮る対象を起こすだけで撮影範囲外の情報が入り得る

## 人手で撮る道は入った

UIA が届かない相手（canvas・ゲーム・OAuth・自動操作が許されない業務アプリ）に
人が操作して撮る道は**実装済み** —— 支援収録 (`gmp shoot`)。
[docs/plan.md](../plan.md) と [CLAUDE.md](../../CLAUDE.md) にある。**ここには残さない**
（実装したものはアイデアではない）。**ウィンドウを撮る部分 (`capture.py`) はそのまま使える。**

残っているのは**自動で駆動するほう**で、人が操作しなくて済めば決定論が戻る。

## やるとしたら

**「render 時オーバーレイ」→「UIA ドライバ」の順。**
1 番目は Android と共通で Web 側にも効くので、この案をやるかどうかに関わらず先に
着手できる。入力は上のとおり通り、初期状態も `app.setup` という口が既にあるので、
**次に潰すのは「環境変数で書き込み先を逸らす手が実アプリで効くか」** —— 効けば
Web と同じ強さの決定論が立ち、効かなければ破壊的な仕込みか VM に落ちる。
**対象を 1 つ選んで実際に試すまで分からない。**

新しく要るもの: `record_windows.py`（`record.py` と同じ `Recorded` を返す）、
`plan.App` に実行ファイルと引数、`settings.SCHEMA` に対象の種別（`web` /
`android` / `windows`）、`gmp doctor` の UIA 確認。
`agent.py` `spec.py` `paths.py` `tts/` `subtitles.py` `ffmpeg.py` は無傷で済むはず。
