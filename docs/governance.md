# 統治と習慣を撮る

[README](../README.md) — アプリの操作ではなく、**そのアプリを使う運用**を題材にする撮り方。
「良きデータのための良き統治」「悪き習慣とは何か」を動画にする。

**新規実装は要らない。** `app.start` と `series.topics`、`determinism.seed` で今日から回る。

**誰に見せるかで詰まるところが変わる。** 社内 Web サービスの研修やスクールの教材に
回すなら、対象の選び方と SaaS を撮るときの壁は [研修と教材に使う](training.md)。

## 前提 —— 統治は映せない。映せるのは統治の帰結

ビートの単位は「1 操作 → すぐ見える結果」なので、
**「命名規約を決めなかった」という一手は撮っても画面に何も起きない**。
統治の失敗は累積的で、複数人にまたがり、遅れて出る。

そこで撮るものを変える。**失敗の瞬間ではなく、失敗が堆積した状態を撮る。**

> 悪い統治のまま 1 年運用したデータベースを仕込んで、それを普通に触ってみせる。
> 検索しても出てこない。同じ意味のタグが 7 個ある。誰がいつ入れたのか分からない。

「命名規約を決めましょう」という説教より、荒れた検索結果を 10 秒見せるほうが効く。
**抽象論を画面で殴れる**のがこの題材の値打ちで、それ以外の伝え方が弱いからこそ動画にする。

3 幕構成（失敗 → 原因 → 正解）はそのまま生きる。ただし **2 幕目で指すものが
アプリの仕様ではなく人の運用**になるので、意識しないと `actions` が空のビートばかりの
紙芝居になる。**「なぜ」も必ず画面で指す** —— 重複した 7 個のタグを `highlight` で
光らせる、という形を保つこと。

## 1. 悪習を選ぶ

操作ミスの失敗例はアプリ固有だが、**悪き習慣は普遍的**なので使い回せる。
Pass1 の仕事も「失敗を発明する」より「一般的な悪習のうち、このアプリで最も刺さるものを
選び、このアプリではどう現れるかを示す」ほうが当たり外れが少ない。

| 悪習 | 画面にどう現れるか |
| --- | --- |
| 語彙が発散する | 同義のタグ・カテゴリが並ぶ。絞り込みがどれを選んでも取りこぼす |
| 自由記述への逃避 | 構造化された欄が空で、備考に全部書いてある。集計も検索も効かない |
| 粒度の不一致 | ある人は 1 行、ある人は 1 ページ。一覧が読めない |
| 削除せずリネーム | 履歴が別物になり、いつ何が変わったか追えない |
| 下書きの放置 | 同じ題目が 3 つあり、どれが正か画面から判断できない |
| 全員が管理者 | 変更者が全部同じに見え、誰に訊けばいいか分からない |

`series.topics` はこの一覧を置くための枠。書いておけば依頼文に載り、シリーズを
機械的に計画できる（`gmp config` で効いているか確認できる）。

**1 本 1 悪習。** 目標尺は既定 90 秒で、堆積した状態を見せるだけで 20〜30 秒使う。
複数を詰めると「散らかっていますね」以上のことが言えない動画になる。

## 2. 荒れたデータを仕込む

この題材では**仕込みデータが主役**になる。撮るものが荒れた状態そのものだから。

[GlossPop](https://github.com/lancard-aikawa/GlossPop) の `docs/video/gloss-scope/serve.py`
と同じ形 —— 収録用のスクリプトで**使い捨てのデータルート**を作り、そこにアプリを
立てる。実データを触らず、何度撮っても同じ画面から始まる。

**仕込みは `app.setup` に置く** (`app.teardown` で片付ける)。`app.start` より前に
走るので、仕込んだデータを開発サーバが読む。仕込みが落ちたら収録は止まる ——
荒れていないデータを撮った動画が出来上がるほうが困る。配信と仕込みが分けられない
スクリプト (serve.py が両方やる形) なら、これまでどおり `app.start` だけでもよい。

データ自体は AI に作らせるのが早い。ソースを読んでスキーマを理解しているので:

```
このスキーマで、命名規約が無いまま 8 人が 1 年入力し続けたらどうなるかを再現する
シードデータを作って。tags の表記ゆれ、notes への逃避、粒度の不一致を含めて。
収録用の使い捨てデータルートに流し込む形にして、seed を固定して。
```

**seed を固定すること。** 生成のたびに荒れ方が変わると、`plan.json` の selector が
指す先が動いて撮り直しのたびに直す羽目になる。生成器が乱数を使うなら `determinism.seed`
と同じ値を渡し、生成済みのデータをファイルとして git に置くほうが確実。

## 3. video.md を書く

構造は既定の 3 幕のまま、狙いだけ運用の話に差し替える。

```yaml
scenes:
  - id: poor
    goal: 1年運用した状態で、担当者が普通に探し物をする（見つからない）
  - id: why
    goal: 検索が効かない理由を、登録されたタグを指しながら説明する
  - id: rich
    goal: 規約に沿って入れ直した状態で、同じ探し物が一発で出ることを見せる
```

**補足には「操作ミスの教材ではない」と明示する。** Pass1 の依頼文には
`spec.GUIDE` から「失敗は狙って作る」が無条件で入る（`ghostmovieplay/spec.py:325`）ので、
書かないと**個人の操作ミスの話に寄せられる**。補足は依頼文の末尾（GUIDE より後）に
入るので、上書きとしては効きやすい。

```markdown
## 補足

これは操作ミスの教材ではない。一人ひとりの操作は全部正しく、
**規約を決めなかったことの帰結**として画面がこうなっている、という話にすること。
誰かの入力を責める画にしない。データは合成で、実在の入力ではない。
```

## 4. 良い側と並べたいとき

同じ操作を 2 つのデータルートで 2 回撮れば 2 本の mp4 になる（`app.start` を差し替えるだけ）。
**ただし `gmp render` は 1 本しか扱わない**ので、左右に並べたければ ffmpeg を自分で叩く。

90 秒に収めるなら並べないほうがいい。**悪い側を実演し、良い側は結果だけ見せる**構成が、
尺の割に一番効く。

## 気をつけること

- **実データを映さない。** `series.avoid` に「実データが映る画面」を書く。
  合成データ + 決定論なので **「これは誰の入力でもない」と言い切れる** ——
  この手の題材には「うちのことを言われている」という反発が付き物なので、
  決定論性がそのまま倫理的な担保になる
- **特定の人を責める画にしない。** 変更者名が映るなら合成名にする
- **視聴者が個人から組織に変わる。** `series.audience` を書き換える。
  「運用を決める人」と「日々入力する人」では刺さる悪習が違う
- **尺が伸びやすい。** 前提の共有が要るぶん長くなる。1 本に詰めず `series.count` で割る

## 効いてくる設定

| 設定 | この題材での役割 |
| --- | --- |
| `series.topics` | 悪習カタログの置き場。シリーズの計画がここから出る |
| `series.audience` | 運用を決める人か、入力する人か |
| `series.avoid` | 実データが映る画面を締め出す |
| `app.start` | 荒れたデータルートを立てる収録用スクリプト |
| `determinism.seed` | 荒れ方を固定する。selector が動かなくなる |
