# 実ブラウザで撮る（サインインの壁を道具の側で外す）

[アイデア](README.md) — 使い捨ての自動化ブラウザではなく、**人がサインイン済みの
ブラウザ**で撮る案。[研修と教材](../training.md)でいちばん効くところ ——
Microsoft 365 / Google Workspace は**自動化ブラウザからのサインインを弾く**ので、
いまは「そこだけ人が撮る」に落ちている。

**まだ何も測っていない。** 下は机上で、**数字を書くときは実際に叩いてから**。

## 分けて考える —— 「駆動」と「起こす」は別の話

| | 何をする | AI | 決定論 |
| --- | --- | --- | --- |
| **駆動**（撮るときに動かす） | plan.json の `actions` を再生する | **入れない** | **要る** |
| **起こす**（台本を作るとき） | 人 or AI の操作を `actions` に変換する | 入れてよい | 要らない |

**この 2 つを混ぜない。** 撮るたびに AI がブラウザを触ると、
[3 段に分けた意味が消える](../../CLAUDE.md)。**AI は 1 回だけ操作して、
出てくるのは台本**（[desktop.md の駆動の当て](desktop.md#人の代わりを-ai-にやらせる駆動の当て)と同じ形）。

## 駆動 —— Playwright を捨てなくてよい

「実ブラウザ」には強さの違う 3 段がある。**下ほど安いが、上ほど本物**。

| | 中身 | 引き換え |
| --- | --- | --- |
| **1. 収録用の永続プロファイル** | Playwright が持つ専用プロファイル。**人が 1 回だけ手でサインイン**して、以後はそれを使い回す | セッションが切れたら人が入り直す |
| **2. 実ブラウザに繋ぐ (CDP)** | 起動中の Chrome / Edge にデバッグポートで繋ぐ。Playwright の `connect_over_cdp` がそのまま使える | **新しめの Chrome は既定プロファイルでのデバッグポートを受け付けない**（別の user-data-dir が要る＝そのセッションは無いかもしれない）。要実測 |
| **3. 拡張として中で動く** | ブラウザ拡張が操作を再生する | 別実装。配布と権限の話が増える |

**1 が本命。** `plan.json` は変わらず、`record` の中で `launch` が
`launch_persistent_context` に変わるだけ。**Pass1 も Pass3 も無傷**。

**ただし決定論の意味が変わる。** いまは「誰がどこから撮っても同じ」だが、
プロファイルを使うと**サインインしている人・テナントで画面が変わる**。
`plan.json` を配っても同じ動画は出ない —— [束を配る](bundle.md)話と正面から
ぶつかるので、**そういう 1 本だと分かる印**（`app.profile` のような欄）が要る。

**会社の端末では塞がれていることがある。** リモートデバッグは管理ポリシーで
禁止できるし、拡張の追加も止められている。**2 と 3 は「使える環境なら」の道**。

## 起こす —— 変換器を作るのがいちばん現実的

**人の操作を `actions` に変換するプログラム**（`plan.json` の
[逆変換](README.md#d-狙って失敗するだけを取り出す)）。**AI は要らない。**

**入口は既にある。** Chrome の DevTools には **Recorder** があって、人の操作を
記録して JSON で書き出せる（1 ステップに selector の候補が複数付く）。
**その JSON を `ACTION_SPECS` に写すだけ**なら、対応表 1 枚で届く。

- 記録するのは**本人がサインイン済みの実ブラウザ**なので、**サインインの壁を
  そもそも通らない**
- 出てくるのは**素の操作の羅列**（無駄な click、座標、待ち）。**削って束ねるのは
  Pass1 の仕事** —— 「この操作列から、失敗 → 原因 → 正解の 3 幕を組んで」
- **selector が本物**。推測で書いた selector は収録時に必ず落ちる、という
  いちばん詰まるところが消える

**AI に操作させるなら、出口は同じ。** ブラウザ操作専用の AI があるなら、
それが吐くのも「操作の列」なので、**変換器の入口が 1 つ増えるだけ**。
道具の側は変わらない。

## 何が解けて、何が解けないか

**解ける。**

- **SaaS の画面が撮れる**（研修のいちばん大きな穴）
- **selector を推測しなくてよくなる**
- **人が撮った 1 本が台本になる** —— サポートの再現手順、業務の手順書

**解けない。**

- **実データが映る。** サインイン済み＝本番のデータ。研修用テナントは相変わらず要る
  （[training.md](../training.md#実データを映さない)）。**むしろ危険は上がる**
- **腐りは止まらない。** SaaS は勝手に変わる。`gmp check` は撮り直せるが、
  **プロファイル頼みの 1 本は CI で回せない**（サインインが要る）
- **配れない。** 同じ `plan.json` が人によって違う画面を出すので、
  [束](bundle.md)としては成立しにくい

## やるとしたら

1. **収録用の永続プロファイルを 1 本試す。** `launch_persistent_context` に変えて、
   手でサインインしてから撮る。**セッションが切れたときに何が起きるか**を見る
   （`app.ready` が待ちきれずに落ちれば正しい）
2. **Recorder の JSON を 1 本、手で `actions` に写してみる。** 対応表が
   何行になるか、何が落ちるか（座標クリック・iframe・shadow DOM）が分かる
3. **1 と 2 が通ってから変換器を書く。** 先に書くと、何を捨てるべきかが分からない

**`gmp check` に載らない 1 本が増えることを、先に決めておくこと。**
[腐敗検知](../check.md)は「撮り直せるから検査できる」で成り立っている。
サインインの要る 1 本は支援収録と同じ `--`（検査していない）に落ちる。
